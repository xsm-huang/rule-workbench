## 4. strict 的作用

TypeScript 的类型只在编译阶段存在。开启 `strict` 后，编译器会更严格地检查空值、函数参数、属性初始化和隐式 `any`。

建议配置：

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "useUnknownInCatchVariables": true
  }
}
```

项目中最直接的收益：

- 接口可能不返回的字段不能直接使用。
- 从数组中按下标取值时，需要考虑不存在。
- 不同状态下的数据可以通过类型区分。
- 不允许用大量 `any` 绕过设计问题。

## 5. type 与 interface

两者都可以描述对象：

```ts
interface User {
  id: string;
  displayName: string;
}

type SchemeStatus = 'DRAFT' | 'PENDING_REVIEW' | 'PUBLISHED' | 'REJECTED';

type SchemeOwner = User & {
  role: 'EDITOR';
};
```

本项目建议：

- 对象形状可以使用 `interface`。
- 联合类型、映射、组合类型使用 `type`。
- 不必把“选 type 还是 interface”当成架构问题，团队一致即可。

## 6. 联合类型与判别联合

普通联合：

```ts
type PricingMode = 'UNIT_PRICE' | 'TOTAL_POOL';
```

判别联合通过共同字段区分不同结构：

```ts
interface UnitPriceRule {
  mode: 'UNIT_PRICE';
  unitPrice: number;
  totalAmount?: never;
}

interface TotalPoolRule {
  mode: 'TOTAL_POOL';
  totalAmount: number;
  unitPrice?: never;
}

type PricingRule = UnitPriceRule | TotalPoolRule;

function getAmount(rule: PricingRule): number {
  if (rule.mode === 'UNIT_PRICE') {
    return rule.unitPrice;
  }

  return rule.totalAmount;
}
```

好处：当 `mode` 是 `UNIT_PRICE` 时，TypeScript 自动知道 `unitPrice` 存在，并禁止同时传入 `totalAmount`。

## 7. 类型收窄

### 7.1 `typeof`

```ts
function formatValue(value: string | number): string {
  if (typeof value === 'number') {
    return value.toFixed(2);
  }

  return value.trim();
}
```

### 7.2 `in`

```ts
interface SuccessResult {
  data: { name: string };
}

interface FailureResult {
  error: { message: string };
}

function getResultMessage(result: SuccessResult | FailureResult): string {
  if ('data' in result) {
    return result.data.name;
  }

  return result.error.message;
}
```

### 7.3 自定义类型守卫

```ts
interface ApiError {
  code: string;
  message: string;
}

function isApiError(value: unknown): value is ApiError {
  if (typeof value !== 'object' || value === null) {
    return false;
  }

  return 'code' in value && 'message' in value;
}
```

注意：类型断言 `as ApiError` 只是告诉编译器“相信我”，并没有执行运行时校验。接口数据仍然需要 Zod 等运行时 Schema 校验。

## 8. 泛型

泛型表示“类型暂时不确定，但不同位置必须保持一致”。

```ts
interface ApiResponse<T> {
  success: boolean;
  data?: T;
  requestId: string;
}

interface PageResult<T> {
  items: T[];
  total: number;
  page: number;
  pageSize: number;
}

type SchemeListResponse = ApiResponse<PageResult<SchemeListItem>>;
```

泛型约束：

```ts
function getById<T extends { id: string }>(items: T[], id: string): T | undefined {
  return items.find((item) => item.id === id);
}
```

这里的 `T extends { id: string }` 表示传入的元素可以有其他字段，但必须存在字符串类型的 `id`。

## 9. keyof、typeof 与索引访问类型

```ts
const statusLabel = {
  DRAFT: '草稿',
  PENDING_REVIEW: '待审核',
  PUBLISHED: '已发布',
  REJECTED: '已驳回',
} as const;

type SchemeStatus = keyof typeof statusLabel;
// 'DRAFT' | 'PENDING_REVIEW' | 'PUBLISHED' | 'REJECTED'

type PublishedLabel = (typeof statusLabel)['PUBLISHED'];
// '已发布'
```

`as const` 会把属性收窄为只读字面量，而不是普通 `string`。

## 10. 常用工具类型

假设存在：

```ts
interface Scheme {
  id: string;
  code: string;
  name: string;
  status: SchemeStatus;
  remark?: string;
}
```

常用工具类型：

```ts
type SchemeDraft = Omit<Scheme, 'id' | 'code'>;

type SchemePatch = Partial<Pick<Scheme, 'name' | 'remark'>>;

type SchemeMap = Record<string, Scheme>;

type SchemeSummary = Pick<Scheme, 'id' | 'name' | 'status'>;
```

- `Partial<T>`：所有属性变成可选。
- `Required<T>`：所有属性变成必填。
- `Pick<T, K>`：只保留指定属性。
- `Omit<T, K>`：排除指定属性。
- `Record<K, V>`：键和值的映射。
- `ReturnType<F>`：取得函数返回值类型。
- `Awaited<T>`：取得 Promise 最终解析类型。

## 11. unknown 与 any

```ts
function parseError(error: unknown): string {
  if (error instanceof Error) {
    return error.message;
  }

  return '未知错误';
}
```

- `any`：基本放弃类型检查。
- `unknown`：可以接收任何值，但使用前必须收窄。

接口错误、`catch` 参数和外部 JSON 更适合先使用 `unknown`。

## 12. null、undefined 与可选字段

```ts
interface SchemeVersion {
  reviewerId: string | null;
  reviewComment?: string;
}
```

- `reviewerId: string | null`：字段一定存在，但审核前值为 `null`。
- `reviewComment?: string`：字段可能完全不存在。

不要随意混用，否则前后端契约会变得模糊。

## 13. 四类模型的区别

### 13.1 数据库模型

反映数据库列和关联关系，例如 `content: JsonValue`。

### 13.2 接口 DTO

反映接口允许接收或返回的数据，必须排除密码摘要等内部字段。

### 13.3 领域模型

反映业务概念和规则，例如 `SchemeStatus`、`RuleRow`、合法状态流转。

### 13.4 视图模型

为页面交互服务，例如每行的本地临时 ID、错误状态、是否展开。

```ts
interface RuleRowDto {
  id: string;
  rangeStart: number;
  rangeEnd: number;
}

interface RuleRowViewModel extends RuleRowDto {
  localKey: string;
  errors: Record<string, string[]>;
  touched: boolean;
}
```

不要把 Prisma 生成的数据库类型直接传给 Vue 页面使用。

# 第 2 天：Vue 3、Router 与 Pinia

## 15. Vue 3 响应式基础

## 15.1 ref

适合基本类型、单个对象引用或需要整体替换的值：

```ts
const loading = ref(false);
const scheme = ref<SchemeDetailDto | null>(null);

scheme.value = newScheme;
```

模板中会自动解包，不需要写 `.value`。

## 15.2 reactive

适合结构稳定的对象：

```ts
const query = reactive({
  keyword: '',
  status: undefined as SchemeStatus | undefined,
  page: 1,
  pageSize: 20,
});
```

不要直接替换整个 `reactive` 对象：

```ts
// 不推荐：会丢失原来的响应式引用
// query = newQuery;

Object.assign(query, newQuery);
```

## 15.3 解构陷阱

```ts
const state = reactive({ count: 0 });

// 普通解构会丢失响应式关联
const { count } = state;

// 需要保持响应式时使用 toRefs
const { count: countRef } = toRefs(state);
```

Pinia Store 解构时使用 `storeToRefs`。

## 16. computed、watch、watchEffect

### computed

从现有状态推导新值，必须保持无副作用：

```ts
const enabledRows = computed(() =>
  editorStore.rows.filter((row) => row.enabled),
);
```

### watch

明确观察某个值，并在变化后执行副作用：

```ts
watch(
  () => editorStore.pricingMode,
  (mode, oldMode) => {
    if (mode !== oldMode) {
      editorStore.clearUnusedPricingFields(mode);
    }
  },
);
```

### watchEffect

自动收集回调中读取的响应式依赖，适合依赖较少的简单副作用：

```ts
watchEffect(() => {
  document.title = `${editorStore.schemeName || '新建方案'} - 规则工作台`;
});
```

本项目不要使用深度 `watch` 整个大型规则对象来持续做完整校验。更合适的做法是：

- 行编辑完成后校验当前行。
- 新增、删除或调整区间后校验当前规则组。
- 提交前执行全量校验。

## 17. props 与 emits

```ts
interface Props {
  row: RuleRowViewModel;
  readonly?: boolean;
}

const props = withDefaults(defineProps<Props>(), {
  readonly: false,
});

const emit = defineEmits<{
  update: [row: RuleRowViewModel];
  remove: [rowId: string];
}>();
```

原则：

- Props 向下传递。
- Event 向上通知。
- 子组件不要随意直接修改父组件对象。
- 复杂编辑器可以通过 Store 或明确的更新函数管理变更。

## 18. Composable

Composable 用于复用有状态逻辑：

```ts
export function useUnsavedGuard(isDirty: Ref<boolean>) {
  onBeforeRouteLeave(() => {
    if (!isDirty.value) {
      return true;
    }

    return window.confirm('当前内容尚未保存，是否离开？');
  });
}
```

适合本项目的 Composable：

- `useUnsavedGuard`
- `useLocalDraft`
- `usePermission`
- `useRequestError`

业务规则校验更适合放入纯函数包，不要为了使用 Composable 而把所有函数都命名为 `useXxx`。

## 19. Pinia 的职责

Pinia 管理跨组件共享的客户端编辑状态：

```ts
export const useSchemeEditorStore = defineStore('schemeEditor', () => {
  const draft = ref<SchemeViewModel | null>(null);
  const dirty = ref(false);
  const fieldErrors = ref<Record<string, string[]>>({});

  function replaceDraft(value: SchemeViewModel) {
    draft.value = value;
    dirty.value = false;
  }

  function markDirty() {
    dirty.value = true;
  }

  return {
    draft,
    dirty,
    fieldErrors,
    replaceDraft,
    markDirty,
  };
});
```

不要把方案列表、详情请求缓存和所有接口状态全部塞入 Pinia。后续使用 Vue Query 管理服务端状态。

# 第 3 天：Node.js 与 HTTP

## 22. Node.js 与浏览器的区别

共同点：都执行 JavaScript，并具有事件循环、Promise 和异步任务。

主要区别：

| 浏览器 | Node.js |
| --- | --- |
| 有 DOM、Window、Storage | 没有 DOM，提供文件、网络、进程 API |
| 面向页面交互 | 面向服务、脚本和工具 |
| 受浏览器同源策略约束 | 服务端主动决定允许哪些来源 |
| 用户可以查看前端代码 | 服务端代码不直接暴露给用户 |

Node 服务不能信任来自浏览器的任何数据，包括隐藏按钮后的请求。

## 25. 异步与错误传播

```ts
async function loadScheme(id: string): Promise<SchemeDto> {
  try {
    return await schemeRepository.findById(id);
  } catch (error: unknown) {
    logger.error(error);
    throw new Error('读取方案失败');
  }
}
```

需要理解：

- `async` 函数一定返回 Promise。
- `throw` 会让 Promise 进入 rejected 状态。
- `await` 只能捕获它等待的 Promise 错误。
- 不要捕获错误后什么都不做。
- 服务层可以抛业务异常，全局异常层负责转换为 HTTP 响应。

## 26. HTTP Method

| Method | 常见含义 | 本项目示例 |
| --- | --- | --- |
| GET | 查询，不应修改数据 | 获取方案列表 |
| POST | 创建或执行动作 | 创建方案、提交审核 |
| PUT | 完整更新指定资源 | 保存完整草稿 |
| PATCH | 部分更新 | 本期可以不使用 |
| DELETE | 删除资源 | 本期不提供正式删除 |

## 27. 常见状态码

| 状态码 | 含义 | 本项目场景 |
| --- | --- | --- |
| 200 | 请求成功 | 查询、保存成功 |
| 201 | 创建成功 | 创建方案 |
| 400 | 请求格式错误 | JSON 或参数格式错误 |
| 401 | 未登录或凭证失效 | Cookie 无效 |
| 403 | 已登录但没有权限 | Viewer 调用创建接口 |
| 404 | 资源不存在 | 方案 ID 不存在 |
| 409 | 当前资源状态冲突 | `baseVersion` 已过期 |
| 422 | 数据格式可解析但业务校验失败 | 区间重叠 |
| 500 | 未预期的服务端异常 | 数据库连接异常 |

不要所有失败都返回 `200` 再在 body 中写失败，也不要所有错误都返回 `500`。

## 28. Header、Cookie 与 CORS

### Header

请求和响应的元信息，例如：

- `Content-Type`
- `Authorization`
- `Cookie`
- `Set-Cookie`
- `X-Request-Id`

### Cookie

Cookie 是浏览器按规则自动携带的小型数据。JWT 放入 HttpOnly Cookie 后，前端 JavaScript 不能直接读取，但浏览器仍会在满足条件时发送。

### CORS

CORS 是浏览器对跨源请求的安全限制，不是登录认证。服务端允许某个 Origin，并不代表这个请求拥有业务权限。

## 29. Node 原生 HTTP 示例

```ts
import { createServer } from 'node:http';

const server = createServer((request, response) => {
  if (request.method === 'GET' && request.url === '/health') {
    response.writeHead(200, { 'Content-Type': 'application/json' });
    response.end(JSON.stringify({ status: 'ok' }));
    return;
  }

  response.writeHead(404, { 'Content-Type': 'application/json' });
  response.end(JSON.stringify({ message: 'Not Found' }));
});

server.listen(3000);
```

写这个示例的目的不是以后不用框架，而是理解 NestJS 最终仍然在处理 HTTP 请求和响应。

# 第 4 天：NestJS 基础

## 31. NestJS 的基本分层

```text
HTTP Request
→ Guard
→ Pipe
→ Controller
→ Service
→ Repository / Prisma
→ Interceptor
→ HTTP Response

任意位置抛出异常
→ Exception Filter
```

简化理解：

- **Module**：组织一个功能模块。
- **Controller**：接收 HTTP 请求，调用用例，返回结果。
- **Service**：编排业务流程。
- **Provider**：可以被依赖注入管理的对象。
- **Guard**：判断请求是否允许继续。
- **Pipe**：转换和校验输入。
- **Interceptor**：包裹处理过程，例如计时、统一响应。
- **Exception Filter**：把异常转换成 HTTP 响应。

## 32. Module

```ts
@Module({
  controllers: [SchemesController],
  providers: [SchemesService, SchemesRepository],
  exports: [SchemesService],
})
export class SchemesModule {}
```

Module 负责声明依赖边界，不应该承载业务逻辑。

## 33. Controller

```ts
@Controller('schemes')
export class SchemesController {
  constructor(private readonly schemesService: SchemesService) {}

  @Get()
  findAll(@Query() query: SchemeQueryDto) {
    return this.schemesService.findAll(query);
  }

  @Post()
  create(@Body() body: CreateSchemeDto, @CurrentUser() user: UserPayload) {
    return this.schemesService.create(body, user);
  }
}
```

Controller 应该保持薄：

- 不直接写 Prisma 查询。
- 不在里面实现区间校验。
- 不在里面判断复杂状态流转。

## 34. Service

```ts
@Injectable()
export class SchemesService {
  constructor(private readonly repository: SchemesRepository) {}

  async create(input: CreateSchemeDto, user: UserPayload) {
    if (user.role !== 'EDITOR') {
      throw new ForbiddenException('当前角色不能创建方案');
    }

    return this.repository.create({
      ...input,
      ownerId: user.id,
      status: 'DRAFT',
    });
  }
}
```

实际项目中，角色判断更适合由 Guard 或权限服务统一处理；示例只是说明 Service 承担业务编排。

## 35. 依赖注入

```ts
constructor(private readonly schemesService: SchemesService) {}
```

Controller 不需要自己 `new SchemesService()`，由 Nest 容器创建和注入依赖。

好处：

- 依赖关系明确。
- 便于替换实现。
- 测试时可以注入 Mock Repository。
- 生命周期由框架管理。

## 36. Guard、Pipe、Interceptor、Filter

### Guard：是否允许继续

```ts
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('EDITOR')
@Post()
create() {}
```

### Pipe：输入是否合法

```ts
@Post()
create(@Body(new ValidationPipe()) body: CreateSchemeDto) {}
```

本项目计划使用 Zod / Standard Schema 进行运行时校验。

### Interceptor：包裹执行过程

适合：

- 统一响应结构。
- 统计接口耗时。
- 附加 Request ID。

### Exception Filter：统一错误响应

将 `ForbiddenException`、领域校验错误和未知异常转换为稳定的错误格式。

## 37. 模块划分

P0 建议只建以下模块：

```text
AppModule
├─ AuthModule
├─ UsersModule
├─ SchemesModule
├─ WorkbenchModule
└─ PrismaModule
```

不要在一开始拆分十几个模块，也不要使用微服务结构。

# 第 5 天：SQL、PostgreSQL、事务与乐观锁

## 39. 关系数据库核心概念

### 主键

唯一标识一行数据，例如 `users.id`。

### 外键

保证关联数据真实存在，例如 `schemes.owner_id` 指向 `users.id`。

### 唯一约束

保证字段或字段组合不重复，例如：

- `users.email`
- `schemes.code`
- `scheme_versions(scheme_id, version_no)`

### 一对多

一个 Scheme 可以拥有多个 SchemeVersion。

## 40. 基本 SQL

```sql
SELECT id, code, name, status
FROM schemes
WHERE status = 'PUBLISHED'
ORDER BY updated_at DESC
LIMIT 20 OFFSET 0;
```

```sql
INSERT INTO schemes (id, code, name, status, owner_id, edit_version)
VALUES ($1, $2, $3, 'DRAFT', $4, 1);
```

```sql
UPDATE schemes
SET name = $1,
    content = $2,
    edit_version = edit_version + 1,
    updated_at = NOW()
WHERE id = $3
  AND edit_version = $4;
```

最后一个 `UPDATE` 同时包含了乐观锁条件。

## 41. 索引

索引可以加快查询，但会增加存储和写入成本。

本项目可能需要：

- `users(email)`：唯一索引。
- `schemes(code)`：唯一索引。
- `schemes(status, updated_at)`：支持状态筛选和时间排序。
- `schemes(owner_id)`：支持负责人查询。
- `scheme_versions(scheme_id, version_no)`：唯一复合索引。

不要给每一列都建索引，也不要给 JSONB 中每个字段提前建索引。

## 42. 事务与 ACID

事务是一组要么全部成功、要么全部失败的数据库操作。

### ACID 简化理解

- Atomicity 原子性：不能只完成一半。
- Consistency 一致性：事务前后约束保持成立。
- Isolation 隔离性：并发事务不会任意互相干扰。
- Durability 持久性：提交后的数据不会因进程重启消失。

提交审核需要一个事务：

1. 检查当前状态和 `editVersion`。
2. 新增 `scheme_versions` 快照。
3. 更新 `schemes.status` 与版本号。
4. 新增 `audit_logs`。

如果第 4 步失败，前 2、3 步也必须回滚。

## 43. 乐观锁

乐观锁不提前锁住数据，而是在更新时检查版本号是否仍然一致。

```sql
UPDATE schemes
SET content = $1,
    edit_version = edit_version + 1
WHERE id = $2
  AND edit_version = $3;
```

- 更新行数为 1：保存成功。
- 更新行数为 0：数据不存在或版本已变化，需要返回 409。

为什么适合本项目：

- 同一方案并不会持续被大量用户同时写入。
- 不需要长期持有数据库锁。
- 冲突时提醒用户重新加载即可。

## 44. JSONB 的取舍

本项目将以下内容结构化存储：

- 方案名称、编号、状态、模式、负责人、更新时间。

将以下内容保存为 JSONB：

- 四个规则组。
- 每组的规则行和 11 个字段。

优点：

- 整套规则可以原子保存。
- 容易生成不可变版本快照。
- 后续增加字段时迁移成本较低。

缺点：

- 不适合频繁按任意规则字段筛选、聚合。
- 数据库层面的字段约束较少，需要服务端 Schema 严格校验。

## 45. Prisma 最小认知

第 0 阶段只需知道：

- `schema.prisma` 定义模型和关系。
- Migration 记录数据库结构变化。
- Seed 写入演示账号和示例方案。
- Prisma Client 执行查询。
- `$transaction` 执行事务。

```ts
await prisma.$transaction(async (tx) => {
  const version = await tx.schemeVersion.create({ data: versionData });

  await tx.scheme.update({
    where: { id: schemeId },
    data: {
      status: 'PENDING_REVIEW',
      currentVersionNo: version.versionNo,
    },
  });

  await tx.auditLog.create({ data: auditData });
});
```

不能因为使用 ORM 就完全不理解 SQL、索引和事务。

# 第 6 天：认证、授权、JWT、Cookie 与安全

## 47. 认证与授权

- Authentication 认证：确认“你是谁”。
- Authorization 授权：确认“你能做什么”。

本项目流程：

```text
邮箱 + 密码
→ 验证用户身份
→ 签发 JWT
→ 写入 HttpOnly Cookie
→ 后续请求解析 JWT
→ 获取用户角色
→ Guard 判断是否允许操作
```

## 48. 密码哈希

数据库不能保存明文密码，也不应该保存可逆加密后的密码。

正确流程：

1. 创建演示用户时，使用 Argon2 或 bcrypt 生成密码摘要。
2. 登录时用库提供的 `verify/compare` 验证。
3. 永远不把 `passwordHash` 返回给前端。

哈希函数会加入随机盐，使相同密码也能产生不同摘要。

## 49. JWT

JWT 通常由三部分组成：

```text
Header.Payload.Signature
```

Payload 可以包含：

```ts
interface JwtPayload {
  sub: string;
  role: 'VIEWER' | 'EDITOR' | 'REVIEWER';
  exp: number;
}
```

注意：

- Payload 只是 Base64URL 编码，不是加密。
- 不放密码、身份证号等敏感信息。
- 服务端必须验证签名和过期时间。
- 本期使用短期 Token，过期后重新登录，不做 Refresh Token。

## 50. Cookie 属性

```text
Set-Cookie: access_token=...; HttpOnly; SameSite=Lax; Path=/; Max-Age=28800
```

- `HttpOnly`：JavaScript 不能读取，降低 Token 被 XSS 直接窃取的风险。
- `Secure`：只通过 HTTPS 发送，生产环境必须启用。
- `SameSite`：限制跨站携带 Cookie，降低 CSRF 风险。
- `Path`：Cookie 适用路径。
- `Max-Age`：有效时长。

使用 Cookie 认证时，Axios 需要根据部署方式配置 `withCredentials`，服务端 CORS 不能使用任意 Origin 与 Credentials 的组合。

## 51. 401 与 403

```text
没有有效身份 → 401 Unauthorized
有身份但权限不足 → 403 Forbidden
```

示例：

- Cookie 过期：401。
- Viewer 调用创建方案：403。
- Editor 审核方案：403。

## 52. XSS、CSRF、CORS

### XSS

攻击者让页面执行恶意脚本。

本项目措施：

- 不使用 `v-html` 展示用户输入。
- Vue 默认文本插值会转义 HTML。
- 不把 Token 放在 localStorage。

### CSRF

攻击者诱导已登录用户的浏览器向目标站点发送请求，浏览器可能自动携带 Cookie。

本项目措施：

- 使用 `SameSite=Lax` 或更严格策略。
- 写操作校验请求 Origin。
- 正式部署保证前后端来源策略明确。

### CORS

控制浏览器是否允许前端读取跨源响应。CORS 不是服务端鉴权，也不能防止非浏览器客户端直接调用接口。

## 53. 前后端权限双重控制

前端：

- 隐藏 Viewer 的“新建”按钮。
- Editor 看不到“审核通过”。
- 无权限路由跳转。

服务端：

- 每个写接口使用 Guard。
- Service 再检查资源归属和状态。
- 不能因为前端没有按钮就省略服务端权限。

## 54. 基础登录伪代码

```ts
async function login(email: string, password: string) {
  const user = await usersRepository.findByEmail(email);

  if (!user || !(await passwordHasher.verify(user.passwordHash, password))) {
    throw new UnauthorizedException('账号或密码错误');
  }

  const token = await jwtService.signAsync({
    sub: user.id,
    role: user.role,
  });

  return { user, token };
}
```

错误提示统一写“账号或密码错误”，避免攻击者判断某个账号是否存在。

# 参考答案与提示

## 59. 第 1 天答案提示

### 判别联合示例

```ts
type PricingConfig =
  | {
      mode: 'UNIT_PRICE';
      unitPrice: number;
      totalAmount?: never;
    }
  | {
      mode: 'TOTAL_POOL';
      totalAmount: number;
      unitPrice?: never;
    };

function getPricingValue(config: PricingConfig): number {
  return config.mode === 'UNIT_PRICE'
    ? config.unitPrice
    : config.totalAmount;
}
```

### 核心口径

- `unknown` 强迫使用者先判断类型，`any` 会传播不安全。
- 判别联合让模式与字段形成类型约束。
- Prisma 类型代表持久化结构，页面需要的是稳定且安全的视图数据。
- `Partial` 修改属性是否必填；`Pick` 选择保留哪些属性。
- `as const` 将值收窄为只读字面量。

## 60. 第 2 天答案提示

- `ref` 通过 `.value` 持有一个响应式值，适合基本类型和整体替换；`reactive` 返回对象代理。
- 大对象深度 watch 会带来不必要的遍历和难以控制的副作用。
- `computed` 是无副作用的派生状态；保存接口属于副作用。
- Pinia 管理编辑交互状态；Vue Query 管理来自服务端的数据及缓存。
- 用户可以绕过前端直接请求接口，因此必须服务端鉴权。

## 61. 第 3 天答案提示

状态码：

1. 未携带登录 Cookie：401。
2. Viewer 创建方案：403。
3. 方案不存在：404。
4. 区间重叠：422。
5. 编辑版本落后：409。

## 62. 第 4 天答案提示

- Controller 负责 HTTP 边界；Service 负责业务用例。
- Controller 直接调用 Prisma 会把传输层和持久化层耦合在一起。
- Guard 判断能不能进入；Pipe 转换和校验输入。
- Interceptor 包裹正常执行过程；Filter 处理异常。
- 依赖注入允许测试时替换 Repository 或其他外部依赖。

## 63. 第 5 天答案提示

- 主键唯一标识当前表记录；外键保证关联记录存在；唯一约束防止业务键重复。
- 索引增加写入和存储成本，因此只为真实查询建立。
- 提交审核中，版本、状态和日志必须全部成功或全部回滚。
- 更新时版本号不匹配代表数据已经变化，因此返回 409。
- 状态需要频繁筛选并有强约束，适合结构化列；复杂规则作为整体快照更适合 JSONB。

## 64. 第 6 天答案提示

- localStorage 中的 JWT 更容易被 XSS 脚本读取，但安全性需要结合完整架构判断，不能只凭存储位置下绝对结论。
- CORS 只限制浏览器读取跨源响应，不证明调用者身份。
- HttpOnly 降低 Token 被读取的风险，但 XSS 仍可能利用用户会话发起操作。
- 服务端必须始终校验权限。
- JWT Payload 可被客户端解码，不能保存密码等敏感信息。
